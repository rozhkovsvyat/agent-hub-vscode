# agent-hub-vscode — контракт модуля

> Canonical instruction set для любых AI-агентов (Claude Code, Codex CLI, Cursor, Grok, Kimi),
> работающих в этом репозитории. Имя `AGENTS.md` — IDE-нейтральная конвенция; рядом лежит
> `CLAUDE.md` (редирект сюда для Claude Code).
>
> 🔴 Брокер требует этот файл в КАЖДОМ созданном worktree
> (`broker/worktrees.py`: «созданный worktree не содержит AGENTS.md»). Без него делегирование
> в scope `plugin` падает целиком. Удалять или переносить файл нельзя.

## Что это за репозиторий

Форк [continuedev/continue](https://github.com/continuedev/continue) → расширение VS Code
**Cukii** (`cukii.cukii-vscode`, displayName «Cukii»). Апстрим объявлен read-only и больше не
развивается, поэтому обратного слияния не будет: этот форк — самостоятельный продукт.

Владелец работает в нём каждый день. Это не полигон: сломанная сборка здесь останавливает
работу человека, а не только агента.

## Граница «наш код / чужой код»

- **Наше** — файлы `cukii*` (21 штука в `extensions/vscode/src`, из них 11 — тесты рядом с
  модулем). Здесь можно и нужно менять всё.
- **Чужое** — остальной апстрим. Правим ТОЛЬКО когда иначе задача не решается, минимальным
  диффом и без попутного переформатирования. Причина не в вежливости: чем меньше расхождение
  с апстримом, тем дешевле читать историю и понимать, что именно наше.
- Каталог `worktrees/` в `.gitignore`. Однажды `git add -A` затащил туда 28 вложенных
  репозиториев как gitlink — не повторять; перед `git add -A` смотреть `git status`.

## Приёмка

Каждому модулю `cukiiX.ts` полагается `cukiiX.vitest.ts` рядом. Прогон:

```powershell
cd extensions/vscode
.\node_modules\.bin\vitest.cmd run src/extension/<файл>.vitest.ts
```

🔴 **Зелёный тест сам по себе ничего не доказывает — нужен мутант-контроль.** Испортить
проверяемое поведение (обнулить тело метода, перевернуть условие), убедиться, что падает
ИМЕННО новый тест и ровно он, вернуть как было. Тест, который не краснеет от сломанного
кода, — тавтология, и её надо переписать, а не считать покрытием.

## Ветки и релиз

- Ствол — `cukii/trunk`. Рабочие ветки: `cukii/<тема>-<yyyymmdd>`, от вендорских агентов —
  `codex/<тема>-<yyyymmdd>`, `grok/…`.
- Правку для УЖЕ установленного релиза ветвим от тега этого релиза, а не от ствола: иначе
  собранный VSIX потянет несвязанные изменения в инструмент, которым человек работает сейчас.
- Версия и сборка — `extensions/vscode/package.json` и его скрипты `prepackage` / `package`.

## 🔴 Заявления о работоспособности

Слова `PASS`, `usable`, `ready`, `complete`, `release` про UI, bridge route или vendor
разрешены только после фактического receipt установленного хоста по точному пути владельца:
`ui_submit → bridge_dispatch → vendor_completed` с наблюдаемым ответом реального вендора.
Зелёные unit-тесты, собранный VSIX, совпавший хеш и отчёт другого агента — промежуточное
evidence, и повышать его до runtime-claim нельзя. Полные правила и приёмка — в глобальном
контракте машины (`~/.claude/CLAUDE.md`, раздел «Claims о release и vendor runtime»).

## Память и след работы

Память машины — MCP `cukii-memory`, она общая для всех оболочек. Перед содержательной
работой — `memory_search` по существу задачи; после — запись в дневник направления. Работа,
не оставившая следа в памяти, считается несделанной.

Разборы ошибок этого модуля идут в память (`agents/mistakes/…`), а не в комментарии к коду.

## Что тут уже ломалось

- **Реле памяти ходило кругом.** На машине-коробке настроенный адрес внешний, поэтому запрос
  уходил через VPN на VPS и по frp-туннелю возвращался в тот же компьютер: 17/20 успехов,
  худшее 10 248 мс против 20/20 и 2 мс у локального порта. Починено выбором плеча
  (`CukiiMemoryUpstream`), см. память по слову «memory-local-first».
- **Сборка VSIX в worktree падает** без зависимостей рабочих пространств
  (`@continuedev/config-types` не находится). Прогонять тесты и собирать удобнее в основном
  чекауте, где зависимости уже стоят.
